# Kabisado operations runbook

Budget rule: **₱0/month, free tiers only.** Never add a card, start a trial, or accept an automatic upgrade on any service below. If a screen asks for one, stop.

## What runs where

| Piece | Service | Notes |
|---|---|---|
| API + built React app | Render Free web service (Docker, built from the repo root) | Same origin, so the login cookie is first-party. Sleeps after about 15 minutes idle. |
| Database | Supabase Free Postgres (**session pooler**, port 5432) | The direct host is IPv6-only and does not work from Render. |
| Wake-up page | GitHub Pages | A static page that wakes the API, then redirects to it. |
| Gemini | **Off** (`GEMINI_ENABLED=false`) | Hard kill switch. Do not enable until the billing setup is verified and Google's terms and age restrictions have been reviewed. |

## Secrets: where they live

Nothing secret is ever committed or pasted into chat.

- `DATABASE_URL` and `JWT_SECRET`: **Render dashboard → Environment** only. `JWT_SECRET` is generated by Render (`generateValue: true` in `render.yaml`).
- Your own machine needs the database URL only for migrations and admin commands; keep it in a local, gitignored file or type it into the shell for that one command.
- Repository variable `VITE_API_BASE` (not a secret): GitHub → Settings → Secrets and variables → Actions → **Variables**.

## First deploy, in this order

1. **Supabase:** create the project (Free plan, no card). Copy the **session pooler** connection string (host ending in `pooler.supabase.com`, port **5432**) and put your database password into it.
2. **Migrate the database first**, from your computer, with that URL. Any 32+ character `JWT_SECRET` works here; it is only needed to load settings:
   ```bash
   cd backend
   DATABASE_URL='postgresql://…@…pooler.supabase.com:5432/postgres' JWT_SECRET='any-32-or-more-characters-here-0123456789' alembic upgrade head
   ```
   (PowerShell: set `$env:DATABASE_URL` and `$env:JWT_SECRET` first, then run `alembic upgrade head`.) The app refuses to start if the database is not at the latest migration, and the error says to run this command.
3. **Render:** New → Blueprint → pick this repo and branch. In the dashboard set `DATABASE_URL` (the same pooler URL). Set `ALLOWED_ORIGINS` to a comma-separated list of the service's own URL **and** your Pages origin, e.g. `https://kabisado.onrender.com,https://<you>.github.io`. Keep `COOKIE_SECURE=true` and `GEMINI_ENABLED=false`.
4. **Pages:** Settings → Pages → Source: **GitHub Actions**. Set the variable `VITE_API_BASE` to the Render URL (no trailing slash), then run the "Publish wake-up page" workflow.
5. **Create the first admin** (see below), then run the verification script.

Always migrate **before** deploying code that needs a new migration. Migration `0002` (accounts) is not designed to be rolled back: it drops the old `email` column and backfills new ones, so treat it as a one-way step and take a manual copy of the data first if the database already holds anything you care about.

## Creating an admin

Admins exist only if you create them from a command line; no web page can. Run it on your computer against the production database:

```bash
cd backend
DATABASE_URL='<session pooler URL>' JWT_SECRET='any-32-or-more-characters-here-0123456789' python -m app.cli create-admin --username <name> --display-name "<Name>"
```

It asks for the password twice (hidden) and prints a **recovery code once**. Store both somewhere safe (a password manager). The admin recovery code is the only way back in if the password is lost.

Other commands:

- `python -m app.cli reactivate --username <name>` re-enables an account its owner deactivated (they cannot do it themselves because they cannot log in).
- `python -m app.cli purge-expired` deletes login/session metadata older than 30 days (also runs automatically at every API start).
- `python -m app.cli purge-legacy --yes` deletes the old per-browser accounts from before logins existed (rows with no password). Run once after migrating if you do not need that old data; without `--yes` it only reports the count.

## Rotating `JWT_SECRET`

Access tokens last 15 minutes and are signed with `JWT_SECRET`; refresh tokens are random and unaffected.

1. Copy the current `JWT_SECRET` value into `JWT_SECRET_PREVIOUS`.
2. Set `JWT_SECRET` to a new random value (32+ characters). Deploy.
3. After about 20 minutes, delete `JWT_SECRET_PREVIOUS`.

Nobody is signed out during the rotation. To sign **everyone** out (suspected leak), change `JWT_SECRET`, leave `JWT_SECRET_PREVIOUS` empty, and run `DELETE FROM sessions;` in the Supabase SQL editor. Access tokens stop working immediately (their session is gone) and every refresh cookie becomes invalid.

## Data retention

- Login and session metadata: deleted after 30 days (privacy notice promises this).
- Study content: kept until the student deletes their account (Account → Burahin ang account), which removes the user and everything attached.
- Throttle rows for failed logins use a hash of the username and IP, not the raw values.

## Known limits (honest list)

- **Free-tier sleep:** the first request after idle can take up to about a minute. The Pages wake-up page exists for this.
- **Latency:** the database is far from Render (see the Phase 0 report: roughly a quarter of a second per query), so the API keeps a small connection pool and keeps round trips per request low. Expect a login to be noticeably slower than a list request (the password hash plus several queries); measure it with the verification script rather than trusting an estimate.
- **No managed backups yet.** Supabase Free does not include them; scheduled encrypted backups are a later phase. Until then, the database is the only copy of student data.
- **Original uploaded files are not stored durably.** The extracted text is in the database; the file itself lives on Render's disk, which is wiped on every restart. Durable storage (Supabase Storage) is a later phase.
- **Gemini is off**, so summaries, flashcards and quizzes come from the offline engine. The consent screen and consent log are not built yet; they must exist before Gemini is switched on.
- **No admin dashboard yet.** `/api/admin/ping` only proves role enforcement.
- **A lost password and lost recovery code cannot be recovered.** There is no email or phone, and admins cannot reset a student's password.
- Render and Supabase may change their free-tier terms. Re-check the limits before relying on them.

## Verifying a deployment

```bash
python backend/scripts/e2e_check.py https://<your-service>.onrender.com
# optional admin check:
E2E_ADMIN_USERNAME=<admin> E2E_ADMIN_PASSWORD=<password> python backend/scripts/e2e_check.py https://<your-service>.onrender.com
```

It registers two throwaway students, checks that they cannot see each other's documents, that a student gets 403 on the admin route, that the cookie refresh works, measures login and list latency, confirms Gemini is off, and deletes the throwaway accounts. Paste the report into `docs/phase2-results.md`.

By hand (a script cannot do these):

1. **Restart** the Render service from its dashboard page. Log in again with an account created before the restart; its documents must still be there.
2. Reload the app page while signed in: you must stay signed in.
3. Check Safari and Firefox as well as Chrome (the `__Host-` cookie), at phone width, and tab through the sign-in forms with the keyboard.
4. Open the Pages URL while the API is asleep: the wake message appears, then you are redirected. Note the time it took.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| API will not start: "Run: alembic upgrade head" | The database is behind. Run the migration (step 2 above). |
| Sign-in works but reloading signs you out | The cookie is not being stored: check `COOKIE_SECURE=true` and that you are on the `https://` Render URL, not another origin. |
| Wake-up page gives up after 90 s | Pages origin missing from `ALLOWED_ORIGINS`, or the API is failing to boot: open the Render logs. |
| "Too many attempts" | Throttling after repeated failures (per username and IP). It clears on its own within 15 minutes at most. |
| Frontend build fails on Render with a missing `lightningcss` binary | Retry the deploy; if it repeats, add `lightningcss-linux-x64-gnu` as an explicit dependency. |
